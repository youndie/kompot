# B-59 — Переключатель «старый клиент» — для любого типа, а не только для демо-плагина

`ClientSwitch` плейграунда показывает деградацию на одном типе — `promo_banner` из демо-плагина:
«клиент, выпущенный раньше» — это `Json` без `demoSerializersModule`. Для типа, который пришёл в
**стандартный** словарь позже (`box` из [B-45](B-45-box-overlay.md), дальше — рельс, разделитель),
честного «старого клиента» на странице нет: модуль стандартных сериализаторов генерируется целиком и
знает всё, что есть в сборке. Пояснения переключателя к тому же называют `promo_banner` по имени.

Заведено из B-45, где AC «плейграунд показывает три состояния деградации для `box`» оказался не про
`box`, а про устройство переключателя.

- **Решение, которое стоит проверить первым:** «старый клиент» как набор проводных имён, которых он
  не знает. Тело перед декодированием проходит через ту же трансформацию, что уже добавляет
  `fallback` (`withServerFallback`): узел незнакомого типа переименовывается в тип, которого нет ни в
  одном модуле, — и декодер делает с ним ровно то, что сделал бы старый клиент. Сериализаторы не
  трогаются.
- Альтернатива — собирать `SerializersModule` без выбранных подклассов — требует знать, какие
  подклассы есть в сгенерированном модуле, то есть второго списка рядом с генератором.
- Не делаем: выбор версии клиента по номеру релиза. Нужна не история версий, а один вопрос —
  «что будет, если этого слова клиент не знает».

- AC: на странице можно выбрать незнакомый тип среди присутствующих в теле (минимум `promo_banner` и
  `box`); три состояния — дыра, заглушка, серверный эквивалент — показываются для выбранного;
  пояснения не называют тип по имени; `DegradationStatesTest` держит три состояния для `box`.
- Якоря: `kompot-playground/src/wasmJsMain/kotlin/io/github/youndie/kompot/playground/ClientSwitch.kt`,
  `.../ServerFallback.kt`, `.../Examples.kt`, `kompot-playground/src/wasmJsTest/.../DegradationStatesTest.kt`.

## Находки

- **Выбрана альтернатива, а не первое решение.** Переименование узла в теле делает то же, что
  старый клиент, но журнал тогда называет выдуманный тип, а не тот, что прислал сервер. «Старый
  клиент» — это сегодняшний клиент, у которого из модуля сериализаторов вынута одна регистрация.
  Второго списка рядом с генератором не понадобилось: модуль перечисляет себя сам через
  `SerializersModule.dumpTo`, и тем же проходом находится класс для реестра рендереров (у «сборки
  без рендерера» и у старого клиента нет рендерера ровно этого типа).
- **Какие слова предлагаются:** типы компонентов из тела, которые знает сегодняшний клиент
  (действия и модификаторы — не компоненты). По умолчанию — самый редкий тип, кроме типа корня:
  без корня сравнивать нечего. Для примера с `promo_banner` это он, для «Layers» — `box`.
- **Замена от сервера идёт за выбранным словом.** Страница снимает свою замену (узнаётся по id
  `<id>-equivalent`) с узлов другого типа и не трогает `fallback`, написанный автором тела.
- **Предел демонстрации:** замена — узел `text`, поэтому при выбранном слове `text` старый клиент
  не рисует и её. Журнал говорит об этом честно (`server_fallback` у узла и `nothing` у замены) —
  это правило §2.1 «заменой называют то, что знает любой клиент», показанное от противного.
- **Проверено:** `DegradationStatesTest` — три состояния для `box` (плюс прежние четыре для
  `promo_banner`), совпадение старого и сегодняшнего клиента на теле без `box` и расхождение на
  теле с ним, выбор слова, переезд замены. Тесты гонялись в Chrome for Testing на Linux-машине
  (`CHROME_BIN`); раньше `wasmJsBrowserTest` там исключался. Четыре мутанта (фильтр не вынимает
  тип, рендерер остаётся, замена не снимается, корень не исключается) — каждый роняет названные
  тесты. На странице пройдены все четыре режима для `box` и смена слова на `text`.

# B-12 — Диагностика: синтаксис, схема, правила тела, деградации

«Экран уезжает без релиза клиента» значит, что ошибку в экране находит не компилятор. Сегодня её
находит либо TCK на живом сервере (`kompot-tck`: `component-id`, `text-spans`, `schema`,
`form-fields`…), либо человек с устройством. В студии четыре из этих источников работают над телом
без сервера, и каждый отвечает на свой вопрос: «это вообще JSON», «это тело по профилю сборки»,
«это тело по правилам, которых схема не выражает», «этот клиент это нарисует».

- **Решение: панель с четырьмя слоями и одним типом записи `Finding(layer, path: JsonPath,
  message, severity)`.**
  1. синтаксис — `SerializationException`, offset → строка/колонка;
  2. схема — `JsonSchemaValidator(schemas, strictProfile, extensionTypes)` по
     `kompot.profile.schema.json#/$defs/KompotComponent` (B-04 даёт путь);
  3. правила тела, перенесённые из `TckRunner` как чистые функции над `JsonElement`:
     id непустой и уникальный; `text` равен конкатенации `spans`; для `KompotFormResponse` —
     `fieldId` схемы ↔ полей экрана ↔ ссылок; паттерны deeplink/url уже в схеме;
  4. деградации настоящего рендера — `onDegraded(kind, originalType)`: `UNKNOWN_COMPONENT`,
     `UNRENDERABLE_COMPONENT`, `UNKNOWN_ACTION`, плюс «корень без `type`» (`originalType == "unknown"`,
     ровно тот случай `call.respond(component)`, ради которого превью принимает строку).
  Потому что каждый слой существует и проверен отдельно; студия их не изобретает, а собирает.
- Клик по записи выбирает узел в дереве (B-11); слои 3 и 4 не требуют от потребителя ничего,
  кроме `schemas`.
- Правила слоя 3 живут в `kompot-spec` как `BodyRules.check(body: JsonElement): List<Finding>`,
  и `TckRunner` вызывает их же — иначе два списка правил разойдутся.
- Альтернатива — гонять `TckRunner` с фейковым транспортом: он требует OpenAPI и ходит по
  маршрутам; для одного тела это лишнее.
- Не делаем: слой словаря проекта (открытые слова, токены кита) — B-19; `etag`, `pagination`,
  `idempotency`, `auth` — остаются TCK.

- AC: тело с дублем id, `text ≠ spans` и типом вне профиля даёт три записи с путями; клик
  выделяет узел; корень, закодированный конкретным сериализатором, даёт запись слоя 4 с подсказкой
  про `respondKompotComponent`; `kompot-tck` использует `BodyRules` и остаётся зелёным.
- Якоря: `kompot-spec/src/main/kotlin/.../{JsonSchemaValidator,BodyRules(новый)}.kt`,
  `kompot-tck/src/main/kotlin/.../TckRunner.kt` (проверки `component-id`, `text-spans`, `form-fields`),
  `kompot-preview/.../KompotPreview.kt` (`failOnDegradation`, `NO_DISCRIMINATOR`),
  `kompot-studio/.../diagnostics/` (новый).

## Итог

`BodyRules` в `kompot-spec` (`componentIds`, `textSpans`, `formFields`, `check`) + `BodyFinding`;
в студии `diagnostics/Diagnostics.kt` — `Finding(layer, path, message, severity)` и панель с кликом,
выбирающим узел. Шесть тестов `BodyRulesTest`, шесть `DiagnosticsTest`; `kompot-tck` зелёный
(11 классов) **без правки ожиданий**; аудиты публикации зелёные; окно проверено запуском на теле,
которое поднимает все четыре слоя сразу.

- **Правила переехали в `kompot-spec` целиком, а TCK стал их вызывать.** В `TckRunner` осталась
  половина, которая действительно его: обойти эндпоинты и назвать, откуда тело. Половина, которая
  проверяет, серверу не нужна была никогда — и студии нужна ровно она.
- **`JsonNode.path` стал `JsonPath`, а не строкой.** Иначе правило и валидатор сообщают об одном узле
  двумя строками, которые совпадают сегодня. Теперь это одно значение; строка — только на выходе.
- **Дубль id репортится на ВТОРОМ вхождении и дальше, а не один раз на id.** Студия подсвечивает узел,
  на который указывает находка, а «id twice» — не узел. В TCK поведение сохранено `distinctBy` по
  сообщению: отчёт для человека хочет фразу один раз.
- **Путь у формы проходит СКВОЗЬ конверт** (`$.screen.children[1]`, а не `$.children[1]`): правило
  ходит по подтереву, и репорт «как есть» указывал бы каждым кликом не туда. Проверяется тестом.
- **Синтаксис — один и в одиночку.** Валидатор, которому дали недопечатанный объект, сообщает об
  отсутствии всего, что собирались набрать дальше: страница находок, ни одна из которых не та.
  Смещение вынимается из текста `SerializationException` регуляркой — kotlinx не отдаёт его иначе;
  хак ограничен: не нашлось число — остаётся исходное сообщение.
- **Деградация — `WARNING`, а не ошибка.** Незнакомый узел, ставший плейсхолдером, — это протокол,
  работающий как задумано; называть его ошибкой значит называть дефектом дизайн. Ошибки в панели
  идут первыми, иначе страница деградаций хоронит одну строку про сломанное тело.
- **Подсказка про `respondKompotComponent`** — только у `originalType == "unknown"`. Отдельный тест
  на отрицательную половину: подсказка на каждой деградации отправила бы всех искать сериализатор,
  который ни при чём.
- У каждого правила в тестах есть контроль: чистое дерево, текст без спанов, текст со сходящимися
  спанами, тело-не-форма. Без них любое из утверждений проходит у реализации, которая ругается на всё.
- `crossReferenceKeys` добавлен в `KompotStudioConfig`: типы правил формы изобретает потребитель,
  тулкит их знать не может, и пустая карта означает, что эта половина проверки просто не выполняется.

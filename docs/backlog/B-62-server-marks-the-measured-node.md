# B-62 — Как сервер помечает узел, который меряет эксперимент?

Выделено из [B-54](B-54-impression-is-composition-not-visibility.md). Там показ стал считаться по
видимости, и появился выбор узлов — но на стороне клиента: предикат
`ImpressionVisibility.track: (KompotComponent) -> Boolean`. Решение B-54 предполагало ещё и
необязательное поле узла, которым **сервер** говорит «вот этот баннер — единица измерения». Этого
не сделано, потому что у узла нет общего места для такого поля:

- `KompotComponent` несёт только `id` и `modifiers`;
- цепочка модификаторов закрыта (SPEC.md §2.3) — новый узел модификатора старый клиент не
  декодирует, это не §3;
- значит, поле — это поле у **каждого** типа компонента во всех модулях, включая чужие, и правило
  «новый тип обязан его нести», которое никто не проверяет.

Вопрос, а не задача: это решение уровня протокола, и у него есть дешёвая альтернатива.

- Варианты:
  - **Соглашение об `id`.** Сервер и так выбирает `id`; клиент пишет
    `track = { it.id.startsWith("promo-") }`. Ничего в протоколе, но соглашение между сервером и
    приложением, которое схема не видит. Записать в SPEC как рекомендацию.
  - **Поле у каждого типа** (`tracked: Boolean?` или `impression: String?` — имя единицы для
    аналитики). §3-совместимо, но размножает поле по всем 18 типам профиля (и по типам приложений) и требует сторожа в `kompot-spec`,
    что каждый тип его несёт.
  - **Обёртка-узел** `tracked { … }` — новый тип компонента с одним ребёнком. Старый клиент
    деградирует его в `Unknown` и **теряет ребёнка** — поэтому только с запасным деревом, как у
    `spacer` (B-47).
- Решает: владелец протокола.

- AC: выбор записан в SPEC (§12 или раздел про аналитику) с причиной; если выбрано поле или
  обёртка — открыта задача на реализацию с тестом «помеченный узел считается, непомеченный — нет».
- Якоря: `kompot-core/src/commonMain/kotlin/io/github/youndie/kompot/KompotComponent.kt`,
  `kompot-client/src/commonMain/kotlin/io/github/youndie/kompot/ImpressionTracking.kt`,
  `kompot-spec/SPEC.md` §2.3, §3.

## Решение — 2026-09-25

Владелец выбрал первый вариант: **соглашение об `id`, записанное в SPEC как рекомендация.**
Протокол не меняется: сервер выбирает `id` отслеживаемых узлов по соглашению с приложением,
клиент выбирает их предикатом `ImpressionVisibility.track`. Поле у каждого типа и узел-обёртка
отвергнуты — первое размножается по всем типам и требует сторожа, второе теряет ребёнка у старого
клиента. Остаток работы — запись в SPEC (раздел про аналитику или §12) с этой причиной и пример в
KDoc `ImpressionVisibility`.

## Находки

- **Записано в SPEC §4.3** (абзац «Измеряемый узел называется через `id`»), а не в отдельном разделе
  про аналитику: такого раздела в SPEC нет, а соглашение — о форме `id`, рядом с правилом о его
  стабильности. Там же — почему отвергнуты поле у каждого типа и узел-обёртка.
- Пример — в KDoc `ImpressionVisibility.track`: `track = { it.id.startsWith("promo-") }`.
- Кода и схемы это не меняет; проверка — сборка CI.

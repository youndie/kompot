# B-21 — Инспектор свойств по схеме

Для бэкенд-разработчика текст — нормальный инспектор. Для дизайнера или PM, который хочет
поменять `spacing` или слово `tone`, — нет. Схема профиля знает про каждое свойство имя, JSON-тип,
`required`, `enum` (для Kotlin-enum), `pattern`, `x-kompot-kind: "token"`; после B-06 — ещё
`description` и `x-kompot-default`. Этого достаточно для панели «выбранный узел → его поля».

- **Решение: правая панель под рендером: для выбранного узла (B-11) — поля из `$defs` его
  типа; редактор по типу: строка, число, boolean, `enum` → выпадающий список, поле-токен →
  список из кита бренда (B-19 знает множество), поле-слово из `config.vocabulary` → список
  слов, действие (`$ref` на `KompotAction`) → под-форма по типу действия; правка пишет
  `JsonObject` по пути и текст (B-16).** Потому что это инспектор Builder.io/Nativeblocks —
  «реестр компонентов управляет инспектором», — только реестр здесь уже сгенерирован из типов.
- Поля, которых нет в схеме сборки (незнакомый тип или лишний ключ), показываются как «сырой
  JSON» без редактора — не теряются.
- Альтернатива — форма по `SerialDescriptor` рефлексией: не видит `x-kompot-*`, не работает для
  неизвестных типов, дублирует то, что схема уже печатает.
- Не делаем: вложенные компоненты не редактируются в инспекторе — для них дерево; список
  строк (`quotaTexts`) — простой редактор «по строке», без DnD.

- AC: выбор `usage_counter_card` показывает `title`, `valueText`, `progress` (число), `state`
  (список `CounterStates.all`), `action` (под-форма `navigate` с `deeplink` по паттерну);
  изменение `state` перерисовывает кадр и текст; свойство без описания показывает имя и тип,
  с описанием — описание из KDoc.
- Якоря: `kompot-studio/.../inspector/{Inspector,PropertyEditors,SchemaFields}.kt` (новые),
  `kompot-spec/schema/kompot.profile.schema.json`, B-06, B-16, B-19.

## Итог

`inspector/{SchemaFields,Inspector}.kt` + `JsonEdits.setProperty`/`removeProperty`. Семь тестов в
`InspectorFieldsTest`; окно проверено запуском; аудиты зелёные.

- **Панель работает над ОПРЕДЕЛЕНИЯМИ, а не над типами провода,** и это то, что делает под-форму
  действия бесплатной: `fieldsFor(schemas, defKey)` одинаково читает свойства компонента и свойства
  `navigate`, а `defKeyFor(schemas, wireType, hierarchy)` переводит одно в другое. Отдельного кода
  для вложенного значения нет вовсе.
- **`type` не поле.** Смена дискриминатора делает узел другим типом — это дело дерева, а не текстового
  поля, и редактор, предлагающий его, предлагал бы сломать узел.
- **Нуллабельный примитив печатается как `["integer","null"]`.** Чтение только первой формы (`type` —
  строка) назвало бы половину свойств тулкита нетипизированными; тест ловит это на `maxLines`.
- **Объявленный словарь бьёт схему.** Схема зовёт открытое поле строкой, потому что протокол
  намеренно оставил его открытым; множество слов — единственное, что знает больше, и оно выигрывает.
- **Значения читаются лексером, а не из разобранного объекта:** панель правит документ, и значение,
  напечатанное заново из дерева, вернулось бы отформатированным иначе, чем было написано.
- **Ключи, которых нет в схеме сборки, показываются, а не теряются** — текст остаётся источником
  правды, и панель, спрятавшая ключ, была бы единственным местом, утверждающим обратное. То же для
  типа целиком: у незнакомого типа полей нет, и панель это говорит.
- **`setProperty` вставляет после `type`,** а не перед закрывающей скобкой: `type` есть у каждого
  компонента и потому единственный якорь, который всегда на месте, — иначе вставку пришлось бы искать
  через любую вложенность последнего значения.
- `removeProperty` уносит ровно одну запятую (тест на добавление и очистку подряд): весь риск сплайса
  в этом.

# B-23 — Экспорт DSL-черновика из тела

Тело, собранное в студии (B-16, B-21, B-22), — JSON; сервер пишет экран на Kotlin DSL
(`kompotScreen { column { text(…) } }`). Дорога обратно — руками. Это направление
`tools/canvas/canvas_tree.py` уже ходит для макета («JSON-дерево — черновик серверного
ответа»); студия может дойти на шаг дальше — до Kotlin.

- **Решение: «Экспорт → Kotlin DSL» печатает черновик из `JsonElement` по слотам схемы: для
  типов toolkit'а — вызовы `column`/`row`/`text`/`button`/`table`/`paginatedList` из
  `kompot-standard/.../Dsl.kt`; для типов потребителя — конструктор data class'а с именованными
  аргументами (имя класса — из `x-kompot-wire-type` ↔ регистрация KSP неизвестна схеме, поэтому
  `CamelCase(wireName) + "Component"` с пометкой «проверь имя»); id печатаются явно, если не
  совпадают с детерминированным (B-07).** Потому что черновик, который компилируется после
  правки двух имён, экономит больше, чем стоит генератор.
- Действия — через `NavigateAction(...)` и прочие конструкторы `kompot-standard`; неизвестное
  действие — `TODO("<type>")`.
- Альтернатива — kotlin-scripting в обратную сторону (исполнять DSL в студии): полный компилятор
  в процессе ради превью, которое и так есть из JSON.
- Не делаем: не генерируем формы (`kompot-forms-standard` DSL связывает поле и компонент одним
  вызовом — черновик из JSON эту связь не восстановит честно); не форматируем ktlint'ом.

- AC: экспорт тела из `kompot-client-tck/corpus/` компилируется в тестовом модуле после
  подстановки импортов; экран konekt экспортируется с `UsageCounterCardComponent(...)` и
  пометкой на имени.
- Якоря: `kompot-studio/.../export/DslExport.kt` (новый), `kompot-standard/.../Dsl.kt`,
  `tools/canvas/canvas_tree.py` (та же задача для макета).

## Итог

`exportDsl` печатает из тела черновик на Kotlin: `kompotScreen { … }` для корневой колонки,
вызовы `column`/`row`/`text`/`button`/`table` для типов, у которых DSL есть, и конструктор
с именованными аргументами для всего остального.

Догадка про имя класса оказалась не догадкой для тулкита: `CamelCase(wireName) + "Component"`
даёт `TextComponent`, `PaginatedListComponent`, `ButtonComponent` — все шесть, и так же точно
`close → CloseAction`, `open_url → OpenUrlAction`. Поэтому пометка «проверь имя» ставится не
на все имена, а только на типы, чьё определение лежит вне схем тулкита: там правило то же,
но компилятор в этом репозитории его не проверяет. Границу проводит файл схемы, а не список.

Токены гадать не пришлось вовсе: `ColorToken`/`TypographyToken` — value class над строкой,
так что ключ с провода и есть ключ в Kotlin. `data object` печатается без скобок — `CloseAction`,
не `CloseAction()`, иначе черновик не компилируется. Неизвестное действие — `TODO("<type>")`,
который возвращает `Nothing` и потому компилируется везде.

`padding.all` — не пятая сторона, а фолбэк на каждую (`node.start ?: node.all ?: 0`
в KompotClient), поэтому он разворачивается в четыре стороны: builder сказать `all` не умеет,
а рендер от этого не меняется. Тест держит обе записи рядом, а не приводит одну к другой:
в день, когда `all` перестанет быть фолбэком, смотреть надо будет именно сюда.

Единственный модификатор, который builder выразить не может, — `background` с `role`. Такой узел
уходит в конструкторную форму, где список модификаторов выписан точно. Исключение названо
поимённо, а не выведено из «ничего не напечаталось»: список, опустевший потому, что писатель
забыл случай, выглядел бы ровно так же.

Про AC. Первый пункт опирался на неверную посылку: в `kompot-client-tck/corpus/` лежат только
кейсы форм (§9.3–9.5), а формы задача сама выносит за скобки — экранных тел там нет. Взял
собственный `sample-screen.json` студии и сделал «компилируется» настоящим: черновик — обычный
исходник `SampleScreenDraft.kt` в тестовом сорс-сете, так что его проверяет компилятор модуля
до того, как запустится хоть один тест. К нему два сторожа: один сверяет, что экспортёр
по-прежнему печатает ровно этот файл (файл объявлен входом таск-задачи — иначе после его правки
тест проходил бы из кэша), второй — что скомпилированный черновик описывает тот же экран, что
и тело. Обоих проверил порчей файла: падают оба.

Второй пункт AC называет потребителя поимённо; в этом репозитории о нём не пишут, поэтому
проверка сделана на синтетическом типе вне профиля — `UsageCounterCardComponent(...)`
с пометкой.

В окне рядом с «Save» появилась кнопка «Kotlin»: пишет `<экран>.kt` рядом с телом. Не в дерево
исходников — куда черновик поедет дальше, решает человек.

Проверено: 9 тестов `DslExportTest` плюс компиляция черновика; полная сборка на WSL; окно
поднято на маке.

### Ручная проверка (03.09.2026)

Экспорт настоящего экрана потребителя показал четыре дефекта, которых не видел тест
на образце: имя функции с дефисом (`fun home-screen()`), конструктор чужого типа внутри блока
строился и выбрасывался (нет `addComponent`), строчный комментарий-пометка внутри `listOf(...)`
съедал следующие элементы, а `Float`-поля печатались `Double`-литералами. Первые три поправлены
в экспортёре; для четвёртого генератор схемы пишет `format: float|double` рядом с `number` —
схема потребителя генерируется на лету, и его `progress` получил `f` без единой правки у него.
Черновик после этого: `fun homeScreen()`, восемь блочных пометок, ни одной строчной,
все дроби с суффиксом.

# B-57 — TypeScript-типы из schema/*.json для клиента не на Kotlin

Самые полезные находки у kompot приходили не из своего сьюта, а от реализаций на другой стороне
провода: сервер на Go, клиент на React. Схемы для них уже есть (`kompot-spec/schema/*.json`,
генерируются, проверяются на совместимость), но читающая сторона на TypeScript пишет типы руками —
то есть заново переписывает то, что схема уже сказала, и расходится с ней молча.

- **Решение: генерировать `.d.ts` из схем** в `kompot-spec` той же задачей, что пишет схемы, и
  класть рядом — с проверкой «сгенерированное совпадает с закоммиченным», как у голденов схем.
  Дискриминированные объединения по `type` — прямо из `x-kompot-contributes`.
- Открытые иерархии (§2.1) в TS выражаются объединением известных вариантов **плюс** ветка
  неизвестного `{ type: string }` — иначе типы обещают закрытость, которой у протокола нет.
- Публиковать ли npm-пакет — не в этой задаче; сначала файлы в репозитории и один потребитель.
- Не делаем: рендерер на React. Это следующая ступень, и её лучше делать потребителю, а не нам.

- AC: `.d.ts` для всех схем в репозитории; проверка в `check` краснеет, если схема изменилась, а
  типы нет; тело из корпуса эталонных тел проходит `tsc` против этих типов.
- Якоря: `kompot-spec/`, `kompot-spec/schema/`, `.github/workflows/build.yaml`.

## Находки

### Итерация 1 — 2026-09-25

**Открытое объединение в TypeScript не проверяет ничего — поэтому файлов два.** Решение пункта
(«известные варианты плюс ветка `{ type: string }`») верно для читающей стороны и бесполезно для
проверки: TypeScript не умеет «любая строка, кроме этих», и ветка незнакомого типа принимает любую
ошибку как незнакомый узел. Проверено, а не выведено: `row` со `"spacing": "wide"` внутри тела
открытый файл принимает. Отсюда `kompot.d.ts` (открытый — для того, кто читает провод) и
`kompot.strict.d.ts` (все иерархии закрыты — для того, кто пишет тела). SPEC «Состав».

**Иерархии не все в профиле.** Профиль перечисляет только часть иерархий; закрытая цепочка
модификаторов и переходы сценария живут в своих модулях — первая версия их не печатала, и `tsc`
отверг сами объявления. Печатаются теперь из собственного `oneOf`.

**Корпуса эталонных тел у тулкита нет** — он принадлежит приложению. Проверяются 8 тел примеров
плейграунда (почти весь словарь) и 18 форм корпуса случаев (`FormSchema`). Тело с типом
демо-плагина (`promo_banner`, вне профиля тулкита) — то, что читает старый клиент, — идёт против
открытого файла; строгий его отверг, что и служило первым контролем.

**Контроли:** в каждом прогоне `tools/ts-check.py` портит вложенный `spacing` и требует отказа
(отказ есть; против открытого файла то же тело прошло бы). Изменение схемы без перезаписи типов —
красный `TypeScriptGoldenTest` (и `ToolkitSchemaGoldenTest`) в `kompot-spec:test`, то есть в `check`.

**npm-пакета нет** — как и решено: файлы в репозитории, `tsc` берётся через `npx` в CI.

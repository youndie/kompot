# Локальное состояние экрана: ресёрч

**Задача** ([B-48](../backlog/B-48-local-state-research.md)). Сегодня любое изменение экрана —
раунд-трип: вкладка, раскрытие секции, «показать всё» идут на сервер и возвращаются `navigate` на
тот же экран (§4.4) или кадром канала (§10). Условная видимость в протоколе есть только у полей
формы (§9.4). Вопрос — какую ступень локального состояния добавить в провод, помня, что добавленное
придётся поддерживать каждой реализации клиента и §15 не даст забрать его обратно.

**Главный вывод.** Рекомендуется **ступень 0, которой в списке B-48 не было: компоненты со своим
состоянием** — `tabs` и `expandable`, по образцу `paginated_list`, которое уже держит состояние под
своим `id` (§4.4). Это единственная ступень, на которой **сервер решает, что увидит старый клиент**:
новый тип узла деградирует через `fallback` (§2.1), а новое поле и новое действие — нет. Ступени
1–3 дают больше, но у всех одна и та же деградация: старый клиент показывает скрытое и не реагирует
на нажатие, и сказать ему «без состояния покажи вот так» серверу нечем. Ступень 4 (выражения) — это
язык, а не поле, и отвергнута ещё в формулировке задачи.

Решение необратимо, поэтому оно вынесено вопросом владельцу (конец документа), а не принято здесь.

---

## 1. Что уже есть

| механизм | где | что даёт без сервера |
|---|---|---|
| состояние узла под `id` | §4.4, `paginated_list` | подгруженные страницы переживают перерисовку; заново присланный узел применяется |
| `visibleIf` поля формы | §9.4, `FormCondition` | поле показывается и прячется от значений других полей, локально |
| `present` (0.38) | §4, `KompotActionPresent` | дерево в листе или диалоге — «подробнее» без запроса |
| `confirm`, `sequence`, `refresh` (0.38) | §4 | подтверждение, цепочка намерений, перезапрос экрана |

Чего нет: **ничто, кроме полей формы, не меняет вид экрана без запроса.** Вкладки, аккордеон,
«показать все 12», переключатель, от которого зависит блок ниже, — всё это сегодня либо разные
деревья (разные экраны), либо форма.

## 2. Что говорит единственный настоящий потребитель

tacku (сервер на Go — то есть уже вторая реализация пишущей стороны) упирается в отсутствие
состояния ровно в одном месте — режим выбора нескольких карточек — и решает его **отдельным
экраном**: «what a selection mode would toggle, this protocol expresses by sending different nodes»
(`server/internal/render/bulk.go`). Там же записано, что это не только обход: доска благодаря
этому остаётся `screen` без ввода, и её можно отдавать условно (кэш, §16.2).

Фильтр списка в tacku — поле формы, и так и должно быть: он меняет **данные**, а не вид, и без
сервера не работает на любой ступени.

Вывод для выбора: спроса, который нельзя закрыть сегодняшним словарём, у реального потребителя пока
нет — есть неудобство (лишний экран, лишний запрос). Это аргумент за самую узкую ступень, а не
против всех.

## 3. Ступени

Проверено для каждой: что добавляется в схему, что делает клиент 0.37 (он же любой клиент, не
обновлённый до этой ступени), и что это стоит второй реализации клиента.

### Ступень 0 — компоненты со своим состоянием

```json
{ "type": "tabs", "id": "settings", "selected": 0,
  "tabs": [ { "title": "Profile", "content": { … } }, { "title": "Security", "content": { … } } ],
  "fallback": { "type": "column", "id": "settings-all", "children": [ … все вкладки подряд … ] } }
{ "type": "expandable", "id": "faq-1", "expanded": false,
  "header": { … }, "content": { … } }
```

- **Схема:** 2 типа в деградирующей иерархии `KompotComponent`, около 7 полей на двоих; ни одного
  нового действия, ни одной ссылки между узлами.
- **Клиент 0.37:** узел неизвестного типа → `fallback`, который назвал сервер (§2.1). Для вкладок —
  все панели подряд, для раскрытия — развёрнутое содержимое. Именно сервер решает, приемлемо ли это
  для конкретного экрана, и может не отправлять `tabs` старому клиенту вовсе.
- **Вторая реализация:** два рендерера и состояние внутри них, как у `paginated_list`. Никакой
  машины вычисления, никакого хранилища экрана.
- **Не покрывает:** зависимость между узлами — «переключатель наверху прячет блок внизу». Внутри
  формы её уже покрывает `visibleIf`, вне формы остаётся сервер.

### Ступень 1 — флаг узла и `toggle`

`hidden: true` у `row`/`column`/`box`, действие `toggle { targetId }`.

- **Схема:** 1 действие, 1 поле × 3 контейнера. Появляется **адресация узла узлом** — по `id`,
  который уже обязан быть уникальным (§4.2).
- **Клиент 0.37:** поле неизвестно → игнорируется (§3) → **скрытое показано**. Действие неизвестно →
  `UNKNOWN_ACTION`, нажатие ничего не делает. Для аккордеона это терпимо (всё раскрыто, заголовки
  мертвы), для вкладок — нет: все панели разом и кнопки, которые ничего не делают. Фолбэка у поля нет.
- **Вторая реализация:** хранилище «id → флаг» на экран, правила жизни (§4 ниже), `toggle` в
  цепочке обработчиков.

### Ступень 2 — переменные экрана и `set_state`

Объявление `state: { "tab": "profile" }`, действие `set_state { name, value }`, поле узла
`visibleWhen { name, equals }`.

- **Схема:** объявлять переменные негде: экран без формы едет **голым деревом** (§16.1), конверта
  нет. Значит, поле у корня (у любого типа, который может быть корнем) или новый вид маршрута
  (§12.1) — то есть изменение формы ответа. Значение — `FieldValue` (иерархия без деградации, §2.2;
  существующих 4 вариантов хватает, новые добавлять нельзя без раскатки).
- **Клиент 0.37:** как у ступени 1, только хуже для вкладок: `visibleWhen` игнорируется у каждой
  панели.
- **Вторая реализация:** хранилище переменных, сравнение значений, вторая система имён рядом с `id`.

### Ступень 3 — условия поверх `FormCondition`

Переиспользовать `equals`/`not_equals` и `FieldValue`, условие — полем `visibleIf` у любого узла.

- **Схема:** `kompot-standard` начинает зависеть от `form-core` — каждый экран тянет формы ради
  видимости. Хуже другое: `FormCondition` — иерархия **без деградации** (§2.2). Сегодня в ней два
  условия; первое же новое («и», «или», «в списке», «больше») — ошибка разбора **всего ответа** у
  клиента, который его не знает. Язык условий, однажды выпущенный в каждый узел, растёт только
  раскаткой клиентов вперёд.
- **Клиент 0.37:** `visibleIf` у узла игнорируется → всё видно.
- **Вторая реализация:** то, что уже есть для форм, но с общим пространством имён полей и
  переменных — и с правилом, что делать, когда имя есть в обоих.

### Ступень 4 — выражения

Арифметика и строки в теле. Это язык со своей грамматикой, типами и ошибками вычисления, и каждая
реализация клиента пишет его интерпретатор. Отвергнута формулировкой задачи; здесь не
рассматривается.

## 4. Жизнь состояния (для любой ступени от 0)

Предлагаемое правило — то же, что §4.4 уже требует от списка, доведённое до значения:

- состояние хранится под `id` узла;
- значение с провода (`selected`, `expanded`, `hidden`) — **начальное**: клиент берёт его при первом
  появлении узла и **заново, если сервер прислал другое значение**, чем в прошлый раз;
- иначе состояние переживает `navigate` на тот же экран, `refresh`, кадр канала (§10) и перезагрузку
  списка — пользователь, раскрывший секцию, не видит, как она схлопнулась от фонового обновления;
- кадр, заменивший узел **другим типом** (§10.3), состояние сбрасывает.

Так §4.4 («заново присланная версия применяется») выполняется буквально — изменившееся значение
сервера побеждает, — а неизменившееся не отменяет действия человека.

## 5. Деградация — сводка

| ступень | чем деградирует | кто решает, что увидит старый клиент |
|---|---|---|
| 0 | новый тип узла → `fallback` | **сервер** |
| 1 | поле игнорируется, действие — `UNKNOWN_ACTION` | никто: скрытое показано |
| 2 | как 1, плюс объявление переменных негде положить без смены формы ответа | никто |
| 3 | поле игнорируется; новое условие роняет ответ целиком | никто; рост языка — только раскаткой |
| 4 | — | — |

«Достаточно ли `UNKNOWN_ACTION`» (вопрос B-48): для раскрытия — да, для вкладок — нет. Способ
сказать «без состояния покажи вот так» у протокола есть ровно один — `fallback` узла, — и он
доступен только ступени 0.

## 6. Рекомендация и что отвергнуто

**Ступень 0**, два типа: `tabs` и `expandable`, со своим состоянием по правилу §4 выше. Ступени 1–3
не закрываются навсегда: следующая ступень — **1**, и её стоит брать, когда появится экран, который
не выражается ни ступенью 0, ни формой (зависимость между узлами вне формы), — с записанным
экраном-примером, а не по аналогии с другими движками.

Отвергнуто:

- **ступень 3** — рост языка условий в иерархии без деградации делает каждое новое условие
  ломающим, а зависимость стандартного словаря от форм — ценой для каждого экрана;
- **ступень 2** — требует изменить форму ответа-экрана ради объявления переменных, при той же
  деградации, что у ступени 1;
- **ступень 4** — язык.

## Вопрос

Решает владелец kompot. [B-49](../backlog/B-49-local-state.md) переписывается под выбранное.

1. **Ступень 0** — `tabs` и `expandable` с `fallback`, состояние внутри узла (рекомендуется).
2. **Ступени 0 и 1** — плюс `hidden` у контейнеров и `toggle`, для зависимостей между узлами вне
   формы; деградация ступени 1 принимается.
3. **Ступени 1–3** — рабочая гипотеза B-49: флаг, `set_state`, видимость поверх условия.
4. **Ничего в 0.38** — локальное состояние уходит из релиза до экрана, которому его не хватает.

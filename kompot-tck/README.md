# kompot-tck

Проверки соответствия протоколу чёрным ящиком по HTTP. Гоняются против **любого** адреса — это
приёмочный набор для реализации сервера на другом стеке.

Нормативные правила, которые здесь проверяются, — в [SPEC.md](../kompot-spec/SPEC.md).

## Что проверяется

| Проверка | Правило |
|---|---|
| `schema` | тело успешного ответа соответствует схеме, объявленной для эндпоинта |
| `auth-required` | защищённый эндпоинт без токена отвечает `401` |
| `component-id` | у каждого компонента непустой `id`, и `id` уникальны в пределах дерева (§4.2) |
| `form-fields` | `fieldId` схемы и экрана сходятся; перекрёстные ссылки ведут на существующие поля (§9.2, §9.3) |
| `etag` | повтор с `If-None-Match` даёт `304` без тела; ETag неизменившегося экрана стабилен (§16.2) |
| `pagination` | обход страниц завершается, каждая страница валидна (§8.2) |
| `navigation` | каждый маршрут графа ведёт на работающий экран (§12.1) |
| `idempotency` | без ключа — `400`; тот же ключ с другим телом — `409` (§16.5) |
| `updates` | записанный поток канала: обрамление SSE и каждый кадр как `UpdateComponentMessage` (§16.6) |

Проверки не бросают исключений, а копят находки: прогон доходит до конца и показывает все
расхождения сразу.

Отчёт печатается и при зелёном прогоне — он показывает, **сколько целей** прошла каждая проверка.
Проверка, не нашедшая ни одного подходящего эндпоинта, проходит молча, поэтому без этих счётчиков
зелёный прогон ничего не значит.

Там же — список **непройденных эндпоинтов** с причиной (`Not walked`). Счётчики отвечают на вопрос
«была ли у проверки хоть одна цель» и не видят соседнего случая: эндпоинт, на который не посмотрела
ни одна проверка, пока остальные держат все проверки занятыми. Чаще всего это адрес с параметром
пути — подставить значение набору неоткуда, — а также `deprecated`, поток вместо JSON-документа и
`submit` без тела в `submitPayloads`. Решать, важен ли пропуск, читателю; молчать о нём нельзя,
потому что молчание неотличимо от покрытия.

Пропуск из-за параметров закрывается конфигом: `pathParameters` и `queryParameters` ключуются
**объявленным** адресом — той строкой с `{...}`, что лежит в описании HTTP. Эндпоинт, адресуемый
именем сущности, иначе недостижим для обхода, а это обычно самое большое дерево, которое отдаёт
сервер.

## Запуск

```kotlin
val spec = KompotSpecResources(root = "my-app-protocol")
val transport = RemoteTckTransport("http://localhost:5000")
val report = TckRunner(transport, TckConfig(schemas = spec.schemas(), openApi = spec.openApi())).run()
check(report.isClean) { report.toString() }
```

Всё, чего набор не может вывести из протокола, приходит через `TckConfig`, и **ничего из этого не
зашито внутри**:

| Поле | Зачем |
|---|---|
| `schemas` | спека вашей сборки: файлы схем по имени, включая профиль |
| `openApi` | описание вашего сервера; виды эндпоинтов читаются из `x-kompot-endpoint-kind` |
| `loginPath` / `loginValues` | как получить токен; `null` — прогон остаётся анонимным |
| `submitPayloads` | тела для submit-эндпоинтов: что отправить, знает только приложение |
| `pathParameters` | чем заменить `{...}` в шаблонном адресе: `"/forms/task/{task}" to mapOf("task" to "TAC-1")` |
| `queryParameters` | query, без которого вызов невалиден, по тому же ключу |
| `recordedUpdateStreams` | записанный `text/event-stream` по адресу, который его отдаёт |
| `extensionTypes` | wire-типы деплоя, если они не объявлены в самом профиле (см. §2.4) |
| `crossReferenceKeys` | в каком поле правила лежит ссылка на соседнее поле формы |

### Свои адреса

Пути в вашем сервере могут быть какими угодно. Опишите его в OpenAPI с расширением
`x-kompot-endpoint-kind` (`screen`, `form`, `page`, `submit`, `patch`, `graph`, …) — набор проверок
применится без единой правки кода. Смысл вида и требования к ответу — в SPEC.md §16.1.

### Осторожно с идемпотентностью

Проверка `idempotency` выполняет **реальную операцию**: до кодов `400`/`409` иначе не дойти —
обработчик сначала валидирует поля и отвечает `422` раньше, чем добирается до заголовка. Она
включается только когда заданы `submitPayloads`. Гонять против тестового стенда.

## Чего здесь нет

**Канал живых обновлений.** `updates_stream` отдаёт `text/event-stream`, а не JSON-документ, и в
слепой обход не входит: переносимой проверки кадра пока нет.

## Устройство

Проверки не знают ни про HTTP-фреймворк, ни про реализацию сервера: единственное, что им доступно, —
`TckTransport` (метод, путь, заголовки, тело). Поэтому один и тот же `TckRunner` гоняется и против
сервера, поднятого в процессе тестом, и против чужого адреса по сети.

### Канал живых обновлений

Единственный вид эндпоинта, до которого слепой обход не дотягивается: тело — последовательность
кадров, а не документ. Проверка работает **по записи**, а не по соединению: положите захваченный
поток в `recordedUpdateStreams`, и набор проверит обрамление (`event:`/`data:`, одно JSON-значение
на событие, отсутствие строк, не принадлежащих ни одному полю) и каждый кадр как
`UpdateComponentMessage` — с тем же строгим профилем внутри, что и у любого экрана.

Чего эта проверка **не** покрывает: кто какой топик получает. Изоляция топиков требует живого
соединения и двух личностей, а `TckTransport` умеет только запрос-ответ. Утечка кадров чужого топика
на сегодня не ловится ничем — это известная граница, а не недосмотр.

# kompot-preview

Писать экран на сервере — иначе писать дерево вслепую: посмотреть на него можно, только запустив
клиент. `kompot-preview` рисует **тело, которое возвращает эндпоинт**, настоящими рендерерами, а
`@Preview` рядом кладёт эту картинку в IDE возле кода, который её строит.

```kotlin
@Preview
@Composable
fun CheckoutPreview() {
    KompotPreview(
        body = myJson.encodeToString(KompotFormResponse.serializer(), checkoutScreen()),
        registry = myRegistry,
        designSystem = myDesignSystem,
        // Форма — не одна картинка: пустая, заполненная и со всеми ошибками — это три.
        state = KompotPreviewState(allFieldsChanged = true),
        json = myJson,
    )
}
```

## Тело, а не объект

Превью берёт тело, а не компонент в руке, и это смысл, а не неудобство: простой `call.respond`
теряет дискриминатор `"type"` у КОРНЯ дерева, так что экран, который прекрасно рисуется из объекта в
памяти, перед человеком деградирует в заглушку. Превью, снятое с объекта, фотографирует работающий
экран, который не работает. По той же причине отсутствующий рендерер останавливает превью, а не
рисует серую заглушку: записанная в скриншот-голден, она стала бы ожидаемым видом экрана.

Тот же вызов фотографирует скриншот-тест, так что превью и голден — один вход и две проверки.

## Skiko

Превью в IDE рисуется через skiko, чья нативная для хоста половина приходит с
`compose.desktop.currentOs`. Она есть в модуле приложения и не может быть в опубликованном: она
прибила бы хост в POM.

## Больше, чем взгляд

[`kompot-studio`](../kompot-studio/README.md) открывает записанные тела сборки потребителя, рисует
каждое в её бренд-рамке и даёт его править — JSON, дерево, свойства из схемы, палитра типов профиля,
— пока рядом идут проверки, которые тело должно пройти.

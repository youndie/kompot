# kompot-client-tck

Двенадцать проверок [набора для сервера](../kompot-tck) обходят сервер. Клиента не проверяло ничто —
хотя нормативных предложений спеки ему адресовано больше, а за ними стоит поведение, которого на
проводе нет вовсе: валидация, видимость, патчи, накопление страниц, шаг сценария, деградация.

Здесь — **корпус случаев**: он держит клиента.

Два корпуса легко спутать, потому что оба — файлы данных с манифестом. Различает их содержимое:
**корпус эталонных тел** (§17) хранит настоящие тела ответов и отвечает на вопрос «как выглядит
ответ»; корпус случаев хранит пары «вход → наблюдаемый исход» и отвечает на «как клиент обязан себя
повести». Первый принадлежит приложению, второй — тулкиту.

## Почему он здесь, а корпус тел — нет

Корпус эталонных тел (§17) показывает, **как выглядит** ответ, и обязан покрыть каждый тип профиля —
поэтому он артефакт приложения. Этот покрывает **правила, а не типы**, и все они выражаются
собственным словарём тулкита. Домена в нём нет, поэтому он едет вместе с протоколом.

## Случай

Вход и наблюдаемый исход:

```json
{
  "id": "9.4-a-hidden-field-leaves-the-payload",
  "clause": "§9.4",
  "title": "...",
  "why": "что ломается, если клиент понял правило неверно",
  "form": { "formId": "f", "fields": [ ... ] },
  "steps": [
    { "step": "set", "fieldId": "kind", "value": { "type": "text_value", "text": "other" } },
    { "step": "blur", "fieldId": "kind" },
    { "step": "patch", "patch": { "updates": { ... }, "clearFields": [ ... ] } },
    { "step": "submit" }
  ],
  "expect": {
    "visibleFields": [ "kind" ],
    "payload": { "kind": { "type": "text_value", "text": "other" } },
    "payloadBlocked": false,
    "errors": { "code": "Three capitals" },
    "noErrors": [ "code" ]
  }
}
```

Каждое поле `expect` необязательно: случай утверждает то, о чём он, и молчит об остальном — иначе
падение называет экран состояния вместо одного правила.

`why` — не украшение. Его печатает отчёт о находке, и читать его будет тот, кто пришёл к падению, а
не к случаю.

`payloadBlocked` отличает **отказ** от **пустоты**: `null` — форма отказалась, пустая карта — в форме
ничего не ввели.

## Адаптер

Всё, что набор знает о клиенте, — семь операций. Та же осанка, что у `TckTransport`: адреса ваши,
язык ваш.

```kotlin
interface KompotFormClient {
    fun load(form: JsonObject)
    fun set(fieldId: String, value: JsonObject)
    fun blur(fieldId: String)
    fun applyPatch(patch: JsonObject)
    fun submit()
    fun visibleFields(): List<String>
    fun errors(): Map<String, String>
    fun payload(): JsonObject?
}
```

Значения пересекают границу как JSON, а не как готовые объекты, и это намеренно: адаптер разбирает их
тем же кодом, что и сам клиент. Корпус случаев, раздающий готовые типы, проверял бы декодер тулкита вместо
декодера реализации.

## Запуск

Случаи едут **внутри артефакта**, поэтому копировать их к себе не нужно — и не нужно знать ни путей,
ни числа файлов:

```kotlin
val report = ClientCorpusRunner(ClientCorpusResources.cases()) { MyClientAdapter() }.run()
check(report.isClean) { report.toString() }
```

Копия корпуса случаев у себя — это способ перестать соответствовать спеке, из которой он взят, и не узнать
об этом.

Клиент создаётся **на каждый случай заново**: состояние, оставшееся от предыдущего, — привычный
способ получить корпус, который ничего не значит.

## Чего он не проверяет

Ничего про отрисовку. Вес, не красящий свою долю; метка в шрифте машины; цвет метки — **всё это
прошло бы зелёным**. Такие дефекты ловятся снимками, а снимки между реализациями не переносятся.

Граница проходит по линии «решение против рисунка». Корпус случаев держит решения.

## Что уже нашлось

Первый прогон нашёл не расхождения клиента, а **четыре случая, написанных мной неверно** по одной
только прозе: `equals` и `required_if` сравнивают с `expectedValue` типа `FieldValue`, а не со
строкой. Это тоже результат: правило, которое нельзя применить, прочитав раздел, — дефект раздела.

И одна строка §9.7 ссылалась на `amount_field.currency` — поле, которое убрали при выносе.

# kompot-client-tck

Двенадцать проверок [набора для сервера](../kompot-tck) обходят сервер. Клиента не проверяло ничто —
хотя нормативных предложений спеки ему адресовано больше, а за ними стоит поведение, которого на
проводе нет вовсе: валидация, видимость, патчи, накопление страниц, шаг сценария, деградация.

Здесь — **корпус случаев**: он держит клиента.

Два корпуса легко спутать, потому что оба — файлы данных с манифестом. Различает их содержимое:
**корпус эталонных тел** (§17) хранит настоящие тела ответов и отвечает на вопрос «как выглядит
ответ»; корпус случаев хранит пары «вход → наблюдаемый исход» и отвечает на «как клиент обязан себя
повести». Первый принадлежит приложению, второй — тулкиту.

## Почему он здесь, а корпус тел — нет

Корпус эталонных тел (§17) показывает, **как выглядит** ответ, и обязан покрыть каждый тип профиля —
поэтому он артефакт приложения. Этот покрывает **правила, а не типы**, и все они выражаются
собственным словарём тулкита. Домена в нём нет, поэтому он едет вместе с протоколом.

## Случай

Вход и наблюдаемый исход:

```json
{
  "id": "9.4-a-hidden-field-leaves-the-payload",
  "clause": "§9.4",
  "title": "...",
  "why": "что ломается, если клиент понял правило неверно",
  "form": { "formId": "f", "fields": [ ... ] },
  "steps": [
    { "step": "set", "fieldId": "kind", "value": { "type": "text_value", "text": "other" } },
    { "step": "blur", "fieldId": "kind" },
    { "step": "patch", "patch": { "updates": { ... }, "clearFields": [ ... ] } },
    { "step": "submit" }
  ],
  "expect": {
    "visibleFields": [ "kind" ],
    "payload": { "kind": { "type": "text_value", "text": "other" } },
    "payloadBlocked": false,
    "errors": { "code": "Three capitals" },
    "noErrors": [ "code" ]
  }
}
```

Каждое поле `expect` необязательно: случай утверждает то, о чём он, и молчит об остальном — иначе
падение называет экран состояния вместо одного правила.

## Словарь `expect` и почему он записан

| ключ | форма | о чём |
|---|---|---|
| `visibleFields` | список `fieldId` | ровно эти поля видимы, остальные — нет |
| `payload` | объект `fieldId → значение` | что уехало бы на сервер |
| `payloadBlocked` | флаг | `true` — валидация не пустила сабмит |
| `errors` | объект `fieldId → текст` | на этих полях именно эти ошибки |
| `noErrors` | **список** `fieldId` | на этих полях ошибок нет |

Таблица здесь не для удобства. Случаи были единственным описанием собственного формата, и читатель,
писавший свой раннер, выводил словарь из тех случаев, которые ему попались, — а ключ, встречающийся в
одном случае и в одной форме, ровно тот, который выводится неверно. Так `noErrors` прочли как флаг:
сравнение не совпало никогда, ветка не выполнилась, случай не проверил ничего и отчитался зелёным
рядом с одиннадцатью настоящими.

Поэтому формат едет со **схемой** — `client-corpus.schema.json`, рядом со случаями, внутри того же
артефакта; её имя называет сам `index.json`. Схема сгенерирована из тех же типов, которыми раннер
разбирает случаи, и golden-тест держит её в этом состоянии: схема, написанная руками, описывает то,
что помнил автор, а этот файл существует ровно для того, кому нельзя прочитать Kotlin.

Объекты в ней **закрыты** (`additionalProperties: false`) — в отличие от схем провода, где §3 требует
обратного. Провод обязан терпеть незнакомый ключ; корпус обязан на нём остановиться, потому что
незнакомый ключ здесь — это не более новый отправитель, а молча непроверенное правило.

## Случай обязан что-то утверждать

Работа набора соответствия ровно одна: падать, когда реализация неправа. Перестаёт он её делать не
тем, что утверждает неверное, а тем, что **не утверждает ничего** — и отчитывается тем же зелёным.

Поэтому раннер считает проверки внутри случая и сообщает о случае, не сделавшем ни одной, как о
находке. Пустые `errors: {}` и `noErrors: []` считаются ничем: это предложение, не назвавшее
подлежащего. Ключ, которого раннер не знает, останавливает разбор, а не пропускается.

Считается это **внутри случая**, а не по прогону: корпус, где один случай из двенадцати мёртв,
показывает одиннадцать проходов и одну тишину, и тишину прячет как раз итог.

`why` — не украшение. Его печатает отчёт о находке, и читать его будет тот, кто пришёл к падению, а
не к случаю.

`payloadBlocked` отличает **отказ** от **пустоты**: `null` — форма отказалась, пустая карта — в форме
ничего не ввели.

## Адаптер

Всё, что набор знает о клиенте, — семь операций. Та же осанка, что у `TckTransport`: адреса ваши,
язык ваш.

```kotlin
interface KompotFormClient {
    fun load(form: JsonObject)
    fun set(fieldId: String, value: JsonObject)
    fun blur(fieldId: String)
    fun applyPatch(patch: JsonObject)
    fun submit()
    fun visibleFields(): List<String>
    fun errors(): Map<String, String>
    fun payload(): JsonObject?
}
```

Значения пересекают границу как JSON, а не как готовые объекты, и это намеренно: адаптер разбирает их
тем же кодом, что и сам клиент. Корпус случаев, раздающий готовые типы, проверял бы декодер тулкита вместо
декодера реализации.

Разбирать их **полиморфным сериализатором**: `FieldValue` — открытая иерархия, и `FieldValue.serializer()`
не существует, поэтому первая попытка не компилируется. Нужен `PolymorphicSerializer(FieldValue::class)`
с тем же `SerializersModule`, что у клиента. Это та же грабля, что и в kompot#44, и здесь она стоит
громкого упоминания: документ читают ровно те, кто пишет клиента.

## Корпус спрашивает, что клиент **отправил бы**

Если этот ответ существует только внутри вызова, который заодно отправляет, — **сначала назовите
его**. Адаптер, собирающий payload сам, проверяет собственную копию поведения, а не поведение
клиента.

Это не гипотеза. Первый адаптер на стороне второй реализации повторил у себя два шага — «пометить всё
изменённым, затем отказать или отправить», — и **три намеренные поломки настоящего клиента оставили
корпус зелёным**. Одна функция, которую зовут и обработчик, и адаптер, — все три краснеют. Прогон,
собранный вторым способом, даёт чистый отчёт о коде, который никто не исполняет; это хуже, чем
отсутствие отчёта.

## Запуск

Случаи едут **внутри артефакта**, поэтому копировать их к себе не нужно — и не нужно знать ни путей,
ни числа файлов:

```kotlin
val report = ClientCorpusRunner(ClientCorpusResources.cases()) { MyClientAdapter() }.run()
check(report.isClean) { report.toString() }
```

Копия корпуса случаев у себя — это способ перестать соответствовать спеке, из которой он взят, и не узнать
об этом.

Клиент создаётся **на каждый случай заново**: состояние, оставшееся от предыдущего, — привычный
способ получить корпус, который ничего не значит.

## Чего он не проверяет

Ничего про отрисовку. Вес, не красящий свою долю; метка в шрифте машины; цвет метки — **всё это
прошло бы зелёным**. Такие дефекты ловятся снимками, а снимки между реализациями не переносятся.

Граница проходит по линии «решение против рисунка». Корпус случаев держит решения.

## Что он держит, по правилам, а не по разделам

[`COVERAGE.md`](COVERAGE.md) — таблица «правило §9 → случаи, которые его держат», сгенерированная и
сверяемая тестом. Правила пронумерованы в самой спеке (`9.4.3`), случай называет те, что держит, и
идентификатор, которого в §9 нет, **валит сборку**: переименованное правило не должно оставить случай
молча указывающим в никуда — так отчёт о покрытии и начинает завышать.

По разделам считать было бы дешевле и означало бы больше, чем измерено: §9.5 — один раздел и шесть
правил, и одного случая под ним хватило бы, чтобы абзац выглядел покрытым.

Третья колонка — про то, чего корпус **не** держит и держать не должен: обязательства сервера
(связность схемы — это `kompot-tck`), отрисовка (снимки), и то, до чего не дотягивается адаптер
семи операций. Без неё «19 из 33» читается как недоделанный корпус, хотя большая часть остатка
никогда не была его работой. Правило, не попавшее ни в случаи, ни в эту колонку, печатается как
**не назначено** — чтобы новое правило §9 нельзя было тихо не заметить.

## Чего в корпусе нет

Правило, на которое не написан случай, проходит по причинам, которых никто не проверял: реализация
может не написать его вовсе, прогнать корпус и услышать, что она соответствует. Поэтому есть тест,
который берёт **все типы, зарегистрированные для провода**, и требует, чтобы каждый встретился хотя
бы в одном случае. Список не ведётся руками — руками ведомый устарел бы при первом же новом правиле,
то есть ровно тогда, когда он нужен.

Первый его прогон назвал четыре: `max_amount_from_field`, `amount_field`, `amount_value`,
`autocomplete_field`. Все четыре теперь покрыты.

Чего этот тест не видит: `amount_input.currencyFromField` — свойство UI-компонента, а не схемы формы.
Оно меняет то, что нарисовано, и через семь операций адаптера не наблюдается вовсе. Это граница
корпуса, а не пробел в нём: см. «Чего он не проверяет».

## Что уже нашлось

Прогон второй реализации — клиента, который к тому моменту работал две недели, — дал **8 находок на
15 случаев, и все одной причины**: клиент отправлял введённое и позволял серверу отказать. Ни
пометки всех полей изменёнными, ни проверки состояния ошибок — §9 держался на проводе и нигде
раньше. Работало это потому, что вторая половина продукта валидирует тоже; стоило это лишнего
round-trip и экрана, говорящего то, что могло сказать поле.

Ни один другой инструмент этого не находил.



Первый прогон нашёл не расхождения клиента, а **четыре случая, написанных мной неверно** по одной
только прозе: `equals` и `required_if` сравнивают с `expectedValue` типа `FieldValue`, а не со
строкой. Это тоже результат: правило, которое нельзя применить, прочитав раздел, — дефект раздела.

И одна строка §9.7 ссылалась на `amount_field.currency` — поле, которое убрали при выносе.
